# API 稳定性契约

> **契约修订号：1**（2026-10-11 冻结）
>
> 本页记录三条**不可破坏契约**。它们不是风格偏好，而是必须在写下第一行实现之前就固定的
> **数据格式与归属约定**。其余 API 在 `1.0` 之前都可以改，这三条不行。

## 为什么要在写代码前冻结

三条契约约束的都是**跨模块的接口形状**，而不是某个模块的内部实现：

- 拾取 id 空间 —— 同时约束几何、降采样、拾取回读三处
- `DrawCall` 描述符 —— 同时约束两条数据通道、合批策略、降采样映射
- `Axis` 归属 —— 同时约束轴、`Chart`、多图表布局、脏标记传播

它们共同的特征是：**后改会同时波及三个以上模块，而且对使用者是破坏性变更**。
等到"用起来发现不对"再改，改动成本已经从"改一行类型"变成"重写一条渲染路径"。

反过来，M1/M2 里那些真正需要靠实践才能定下来的东西（轴刻度布局的细节、
`Chart` 门面上的方法名、tooltip 的样式接口）**故意不在这里冻结** —— 约束提前收紧
是另一种浪费。

## C1 · 拾取 id 空间

拾取的做法是额外跑一趟 pass，把每个可拾取实体的 id 写进颜色附件，再用 `readPixels`
把鼠标位置的整数读回来。因此 id 是**唯一的回读通道**，它的编码规则必须全局统一。

### 规则

1. id 是 `uint32`，取值 `[0, 2^32)`。**0 保留**，恒表示"未命中"，对应清屏色
   `(0, 0, 0, 0)`。**任何实体不得领取 0。**
2. id 在整个 `Renderer` 内是一条**全局单调整数轴**，不按 `Chart`、不按图层、不按系列分域。
3. 可拾取实体在注册时领取一段**连续**区间 `[idFirst, idFirst + idCount)`。
4. `idCount` 的语义由实体类型决定：

   | 实体类型                               | `idCount`          | `id − idFirst` 的含义 |
   | -------------------------------------- | ------------------ | --------------------- |
   | 折线 / 散点                            | 当前参与拾取的点数 | 点索引                |
   | 系列级图元（整块面积、单根柱、阈值线） | `1`                | 恒为 0                |
   | `pickable: false` 的实体               | 不领取             | —                     |

5. 同一时刻存活实体的区间**两两不重叠**。实体销毁后区间**归还空闲池**，可被新实体复用 ——
   唯一性是"当前帧的"，不是"进程生命周期的"。
   ⇒ **因此拾取结果必须与产生它的那一帧的 `实体 → 区间` 映射一起解释，不能跨帧缓存 id。**
6. id 的分配顺序与渲染顺序**互不影响**，两者是独立的两件事。
7. 几何若来自降采样结果，`idCount` 按**降采样点数**计，`id − idFirst` 指向降采样索引；
   回原始点的唯一通道是 `DownsampleResult.srcIndex`。

### 不可破坏的理由

回读到的只是一个整数，它必须能**唯一还原**成 `(实体, 点索引)`。
一旦按 `Chart` 或按图层分域，"图层 0 的点 5"这个说法在全局就有二义性 ——
而多 `Chart` 共享同一 `Axis`、或多图表分屏，恰恰是本库的核心场景。
二义性无法在上层弥补，只能改回读格式，那是破坏性变更。

### 违反后的后果

| 违反               | 后果                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| 0 当作合法 id      | 清屏区域与"第 0 个点"不可区分；在空白处与抖动时拾取会返回错误的点        |
| 按 `Chart` 分域    | 多图表分屏 / 共享序列时无法分辨来源，拾取结果不可用                      |
| 按图层分域         | 同一图层被多个 `Chart` 引用时冲突                                        |
| `idCount` 不用点数 | 逐点拾取退化为系列级拾取，十字光标读数**无法实现**                       |
| 区间跨帧缓存       | 实体销毁后区间被复用，旧 id 会命中新实体 —— 这是那种"偶发且难复现"的错误 |

### 容量上限与诊断（不静默）

可用 id 数是 `2^32 − 1`（0 被保留）。按最坏情况估算：

| 单系列点数 | 同屏可拾取实体上限 |
| ---------- | ------------------ |
| `10^6`     | 约 4 295 个        |
| `10^7`     | 约 429 个          |
| `10^8`     | 约 **42 个**       |

超限时**必须报诊断** `picking/id-space-exhausted`（`diagnostics: 'throw'` 时抛出），
并把超出的实体降为系列级拾取（`idCount = 1`）。精度下降但仍有反馈 ——
**绝不静默回绕**（回绕会让拾取命中完全错误的实体，比"拾取不到"危险得多）。

这个降级只动表现层的拾取精度，**不触碰数据层**，符合降级阶梯的硬边界。

## C2 · `DrawCall` 描述符

`DrawCall` 是场景层每帧产出的东西，`Renderer` 的 `DrawList` 消费它。
它是几何与绘制之间的**唯一接缝**，因此也是"两条数据通道会不会分叉"的决定点。

### 规则

1. `DrawCall` 是**一次 GL 绘制所需的最小完整描述**：program key、属性布局、
   缓冲/纹理绑定、实例数、uniform 值、id 区间，以及"点数据来源"。
2. 两条数据通道（`attribute` / `texture`）**共用同一个描述符类型**。
   通道差异只允许表达在"点数据怎么取"**这一个字段**上。
3. 描述符是**每帧构造的短命对象**，不是持久状态。持久状态归 `Series` 持有。
   热路径上禁止为描述符分配内存（预分配 + 复用）。
4. 描述符**必须携带 id 区间**（见 C1），否则拾取无法从 id 反查实体。
5. 几何若来自降采样结果，描述符**必须携带 `srcIndex` 引用**。
6. 描述符必须携带**可合并性信息**：相同 `(program key, 属性布局, 缓冲)` 的描述符
   必须能被合并成一次 draw call。**因此颜色与 id 偏移必须走 per-instance 属性，不得走 uniform。**
7. 描述符描述"画什么"，**不描述"画在哪"**。视口与裁剪属于 `Chart` 的布局层。

### 不可破坏的理由

- **通道分叉是本项目最容易被低估的返工源。** 如果 M1 只做 `attribute` 通道，
  M2 补 `texture` 通道时，着色器、拾取、降采样会各写两套实现 ——
  而且两套实现还得保持像素级一致。共用描述符是把"通道差异"钉死在一个字段里的唯一办法。
- **合并性必须写进描述符**，draw call 预算才是一个可断言的结构性门禁，
  而不是事后优化的结果。

### 违反后的后果

| 违反                  | 后果                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------- |
| 颜色走 uniform        | 8 条线的仪表盘从 1 次 draw 退化为 8 次，32 次/帧的预算立即失效                                             |
| 描述符不带 `srcIndex` | 大数据量下降采样后拾取返回**错误的点**；且这个错误在数据量小时看不出来（小数据不降采样），只在生产环境暴露 |
| 描述符不携带 id 区间  | 拾取 pass 与主 pass 使用不同的实体集合，回读结果无法解释                                                   |
| 描述符成为持久状态    | 脏标记模型失效：一帧没画的图层会残留上一次的绑定                                                           |

## C3 · `Axis` 的归属

### 规则

1. `Axis` 由 `Renderer` 创建并拥有（`renderer.createAxis()`），**不是** `Chart` 的成员。
2. 一个 `Axis` 可被**任意多个** `Chart` 引用；引用期间 range 天然同步 ——
   它们是**同一个对象**，同步不靠事件广播。
3. `Axis` 的销毁走**引用计数**：最后一个引用者释放时才真正销毁。
   `Chart.destroy()` **释放它持有的引用**，不销毁被引用的 `Axis`。
4. `valueToPixel` / `pixelToValue` 是**纯函数**：不读 GL、不读 DOM 布局、不产生副作用。
   因此可单测，也可在 Worker 中使用（分桶降采样需要它）。
5. `Axis` 的 range 变化必须经脏标记 `Transform` 传播到 LOD 重算与几何重传；
   `Series` 不得直接读 `Axis` 内部状态绕过脏标记。
6. `Axis` 的 `type`（`linear` / `log` / `time` / `category`）创建后不可变更；换类型 = 新建一个 `Axis`。

### 不可破坏的理由

- **工业分屏"4 个图表 X 轴同步滚动"是刚需。** 若 `Axis` 归属 `Chart`，同步只能靠事件广播
  互相 `setRange`：每帧 N×N 次通知，且容易循环触发。提升到 `Renderer` 后同步成本为 **0**
  （同一个对象），代价只是使用者多写一行 `renderer.createAxis()`。这笔交易是划算的。
- **纯函数是 Worker 化的前提。** 分桶降采样必须知道 `x → 像素桶` 的映射；
  如果 `valueToPixel` 依赖 canvas 尺寸缓存，Worker 里就算不了，10⁷ 点首帧 `< 1.5 s` 守不住。

### 违反后的后果

| 违反                              | 后果                                                                    |
| --------------------------------- | ----------------------------------------------------------------------- |
| `Axis` 归属 `Chart`               | 共享轴要靠广播；同步延迟与循环触发无法根治，"共享轴"在 API 上也无法表达 |
| `Chart.destroy()` 直接销毁 `Axis` | 第一个 `Chart` 销毁后其余图表全白 —— 引用计数漏掉时的典型表现           |
| `valueToPixel` 非纯函数           | 降采样只能回主线程，大数据首帧预算失守                                  |
| `Series` 绕过脏标记读 `Axis`      | 缩放时 LOD 不重算，画面停在旧层级 —— "看起来在工作但结果是错的"那类 bug |

## 变更流程

这三条契约 **由测试兜住，不靠自觉**：

| 契约 | 由什么门禁兜住                                                                |
| ---- | ----------------------------------------------------------------------------- |
| C1   | id 空间单测：0 恒未命中、存活区间不重叠、销毁后区间可复用、超限必报诊断       |
| C2   | draw call 预算门禁：8 系列合并后仍为 1 次；空图层为 0 次                      |
| C3   | "两个 `Chart` 引用同一 `Axis` 后各自 `destroy()` 不泄漏"单测；`Axis` 引用计数 |

修改契约的规则：

1. 契约修订号在本文档顶部，**改一次 +1**。
2. 每次改动必须在 [`CHANGELOG.md`](https://github.com/Quxiaobaia/as-charts/blob/main/CHANGELOG.md)
   的 `Unreleased` 段落下以 **BREAKING** 标注：改了什么、为什么、使用者需要改什么。
3. `1.0` 之后修改契约需要有**重大版本号**推进。`0.x` 期间允许改，但同样要记录并给出迁移说明。
4. 改契约时**先改测试**：门禁红了才说明契约真的变了，而不是文档与实现漂移了。

## 明确**不**在这儿冻结的部分

避免把约束收得过早 —— 以下都留给实现去定，`0.x` 期间可以随时改：

- `Chart` / `Series` 门面上的方法名与选项对象形状
- 轴刻度的布局细节、标签密度策略、`tickFormat` 的具体签名
- `Tooltip` / 图例 / 控件的样式接口
- 降级阶梯的具体档位数与阈值（`L0`–`L5` 的**边界条件**已定，但触发参数属于调参）
- 包体积与性能的具体数字（进 CI 作为门禁，但会随实现调整）

## 当前实现进度

三条契约是实现目标，不是既成事实。落地位置：

| 契约 | 计划落地位置                                                                                        | 里程碑    |
| ---- | --------------------------------------------------------------------------------------------------- | --------- |
| C1   | **分配半边**：`src/core/IdSpace.ts`；**读回半边**：`src/renderer/Picker.ts`、各 `Series` 的 id 领用 | M1-b / M2 |
| C2   | `src/core/DrawCall.ts`、`src/core/DrawList.ts`、`src/layers/LineLayer.ts`                           | M1-b ✅   |
| C3   | `src/shell/Axis.ts`、`src/shell/Chart.ts`                                                           | M1-c      |

**C2 在 M1-b 落地，并且真的经受了它被设计出来要经受的那次检验**：两条数据通道共用同一套描述符，
`isMergeable` 逐字段比较（而不是相信生产者给的一个 key），单系列恒为 1 次 draw call。
三条契约的强制执行结果：

- **C1 规则 4/5 迫使 id 区间被真正分配**，而不是编造一个看起来对的区间。因此 `IdSpace` 的
  **分配半边提前**到 M1-b：一个编造的区间在所有单测里都正确，直到出现第二个图层为止。
  读回（`Picker`）留在 M2 —— 那才是需要 framebuffer 的一半。
- **C1 规则 1（0 恒未命中）由构造保证**：自由链从 1 开始，`allocate` 永远够不到 0。
  空间耗尽时**降级到系列级拾取**（`count: 1`），不环绕 —— 环绕会让 id 指向**另一个实体**。
- **C2 规则 7（描述符不说画在哪儿）**带来一条必须写下来的不变量：一次 `flush` 只能发生在一个
  布局区域内。M1-c 的 `Layout` 会为每个区域持有一个 `DrawList`，或在区域之间 flush；
  跨 `scissor` 变更的列表会把第二个图的几何画进第一个图的视口。
- **C2 的 `instanceFirst` 不是元数据，是校验位**：WebGL2 没有 `baseInstance`，
  所以合并后的 run 只有从实例 0 开始才可绘制（见 `DrawCall.ts` 的说明）。
